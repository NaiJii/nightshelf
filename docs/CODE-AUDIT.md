# Source audit — 2026-10-21

## Scope and limits

Reviewed the current working tree, including the features already uncommitted before this audit: all 56 production TypeScript/TSX files, four local Android modules, their manifests/Gradle configuration, both config plugins, the build workflow/script, and the regression harnesses. The source/config/test inventory under `src`, `modules`, `plugins`, `scripts`, and `.github` contains 92 files. Also checked package/configuration, tracked-file inventory, ignore rules, and existing documentation. Generated native projects, dependencies, binary assets, credentials, build outputs, and research snapshots are not application source and were excluded.

This is a static source audit with executable regression checks, not Android profiling, a live provider compatibility check, or a physical-device acceptance test. Costs below follow from the code paths; their real time and memory impact have not been measured. Existing unfinished features were preserved. No build, release, dependency change, storage migration, or UI redesign was performed.

## Open findings, in recommended order

P1 means potential data loss or a substantial cost on large libraries. P2 means a localized performance, correctness, or maintenance problem. These remain open because fixing them requires decisions or behavior changes beyond an equivalent simplification.

| ID | Priority / status | Evidence and consequence | Smallest useful next step |

| A01 | P1 · open · durability | `storage.ts` (`savePosition`, `saveCatalog`, preferences/read/saved/download writers) writes entire JSON files directly. A process kill, full disk, or concurrent headless/foreground writer can leave truncated data or lose another writer's changes. Several readers then fall back to empty state. Native transfer state already uses temporary-file replacement. | Introduce an atomic metadata writer and test interrupted writes; separately define ownership/serialization across JS runtimes. Atomic rename alone does not solve lost updates. |
| A02 | P1 · open · download cost | `TransferEngine.kt:37–46,79–130`: automatic downloads repeatedly walk the entire library for storage limits. The JS automatic-download guard in `app-state.tsx:89` also calls `libraryBytesAsync` on every guarded request. | Profile a large automatic job, then maintain a shared usage/reservation ledger with periodic reconciliation. ## Areas checked with no additional change justified

- Library, Explore and chapter lists already use `FlatList`; Home deliberately renders bounded groups. No blanket virtualization rewrite is needed. Storage and the download drawer still map all rows; consider virtualization only if real use/profile counts warrant it.
- Request controllers, debounce cleanup, paging generation guards and bounded discovery/session caches already exist. Provider switching cancels discovery work. Story-detail requests are deduplicated and run asynchronously but are not tied to the provider controller; shared foreground priority may outlive the initiating screen. Include this lifecycle in future cancellation work rather than adding another global busy flag.
- Queue cancellation waits for writers; held bulk jobs preserve explicit user pause/cancel intent. Do not simplify those leases into a boolean.
- Native file targets are constrained to the library; updater files/signers/package/version/ABI/checksums are validated. Reader HTML escapes content and permits local images only. Verification cookies are restricted to challenge cookies for the supported host. No access-control bypass was introduced or tested.
- Build workflow is manual, uses standard GitHub runners, verifies signing/ABI, and deletes its temporary keystore. No credential file appears in the tracked-file inventory. Pinning third-party Actions to commit SHAs would improve supply-chain reproducibility, independently of app behavior.
- Backup restore validates before writes and attempts rollback; it does not make multiple-file writes atomic, and rollback itself can fail on a full disk. Do not describe it as a transaction.
- No dependency removal was justified from source imports alone: Expo/plugins/autolinking may require modules not directly referenced by screens.
